# 蓝牙能力探针（btprobe）

在真机上实测两件决定「无线连接能不能由普通应用实现」的事：

1. **RFCOMM 监听的实际通道号**。无线连接要车机开两个不加密的 RFCOMM 监听：
   - A：UUID `0000FE35-0000-1000-8000-00805F9B34FB`，带服务记录，手机用 SDP 查通道号；
   - B：认证阶段再开，默认 UUID `0000FE36-0000-1000-8000-00805F9B34FB`。车机要把 B 的**实际通道号**通过协议告诉手机，
     手机按通道号直连，不查 SDP。

   公开接口拿不到监听的实际通道号，要看反射等办法在这台设备、这个 targetSdk 下能不能用。
2. **本机真实蓝牙地址**。二维码里要放车机的真实地址，普通应用一般只能读到占位值 `02:00:00:00:00:00`。

这是独立的小应用：不依赖其他模块，也不进 OpenHC 安装包。

## 两个风味

| 风味 | targetSdk | 包名 | 桌面名称 |
|---|---|---|---|
| `t36` | 36（与正式应用一致） | `io.github.gcbond.openhc.btprobe.t36` | 蓝牙探针 t36 |
| `t26` | 26 | `io.github.gcbond.openhc.btprobe.t26` | 蓝牙探针 t26 |

两个风味的清单和代码完全相同，只差 targetSdk。系统按应用的 targetSdk 决定放行哪些隐藏接口，所以把两个装在同一台设备上
各测一遍，差别就是 targetSdk 造成的。minSdk 都是 23（安卓 6.0）。

## 构建与安装

```sh
./gradlew :tools:btprobe:assembleDebug
```

产物：

- `tools/btprobe/build/outputs/apk/t36/debug/openhc-btprobe-t36-debug.apk`
- `tools/btprobe/build/outputs/apk/t26/debug/openhc-btprobe-t26-debug.apk`

安装（两个包名不同，可以同时装）：

```sh
adb install -r openhc-btprobe-t36-debug.apk
adb install -r openhc-btprobe-t26-debug.apk
```

不方便用 adb 的车机：把 apk 拷到 U 盘，在车机的文件管理里点开安装。

## 怎么用

0. 能用 adb 的话，先确认没人放开过隐藏接口限制，否则这台设备的结果不代表普通设备：
   `adb shell settings get global hidden_api_policy`（安卓 9 查 `hidden_api_policy_pre_p_apps` 和
   `hidden_api_policy_p_apps`）和 `adb shell settings get global hidden_api_blacklist_exemptions` 都应输出 `null`。
   探针的「系统信息」里也会自查这几项，读不到时记「跳过」。
1. 先在系统里打开蓝牙。
2. 打开「蓝牙探针 t36」，点「开始检测」。安卓 12 及以上会申请「附近的设备」权限（`BLUETOOTH_CONNECT`、
   `BLUETOOTH_ADVERTISE`），请允许。拒绝了界面会提示，也能一键打开本应用的系统设置；检测照样进行，
   需要权限的项会记成「异常」。
3. 各项检测几秒内跑完。之后默认保持所有监听 60 秒（开关可关），这段时间可以用另一台设备来连、或者查 dumpsys
   （见下文「核对通道号」）；点「停止等待」可提前结束。最后关闭所有监听。
4. 换「蓝牙探针 t26」再测一遍。

看结果：

- **屏幕**：每项显示 成功 / 失败 / 异常 / 跳过 和具体值，文字可以长按选择。
- **复制全部结果**：纯文本，按分组列出。
- **保存到文件**：存到 `Android/data/<包名>/files/btprobe-<风味>-<时间>.txt`，例如
  `adb pull /sdcard/Android/data/io.github.gcbond.openhc.btprobe.t36/files/`。
- **logcat**：每项一行，标签 `OpenHC-BtProbe`：`adb logcat -s OpenHC-BtProbe`。

**地址的显示规则**：屏幕上是完整值；复制、存文件、logcat 里的本机地址和对端地址只留第一段和最后两段
（如 `AA:**:**:**:EE:FF`），`02:00:00:00:00:00` 这类占位值不打码。即便打了码，结果里仍有型号、系统版本号等真实设备信息，
**不要提交进仓库，也不要原样贴到公开的 issue**。

## 状态的含义

| 状态 | 含义 |
|---|---|
| 成功 | 拿到了能用的值：通道号在 1～30 内；地址格式正确且不是占位值 |
| 失败 | 调用没出错，但值不能用：例如通道号是 -1、地址是 `02:00:00:00:00:00` 或读到空 |
| 异常 | 调用抛了异常：被隐藏接口限制拦下、权限不足、IO 错误等，后面附异常类名和原因 |
| 跳过 | 这台设备或这次检测不适用（例如安卓 10 以下没有 `getPsm()`） |

反射找不到成员（`NoSuchFieldException` / `NoSuchMethodException`）有两种可能：成员存在但被隐藏接口限制拦下，
或者这个系统版本根本没有这个成员。探针在安卓 9 及以上打开了系统自带的 StrictMode 非 SDK 接口检测，
每次访问隐藏接口系统会报一次成员签名：报了就是「成员存在，被拦下」；没报多半是「没有该成员」。
「拦下的访问也会上报」是按设计推断的，**未经真机验证**。检测开始时还会先自检一次：查一个各版本都放行的隐藏字段，
看监听有没有记到；没记到，「系统信息」里的自检项和末尾的汇总项都会记「失败」，这时前面「多半没有该成员」的说法不可信。
**一切以 logcat 里的 `Accessing hidden ...` 告警行为准**，探针会把本进程的相关告警行附在结果末尾；读不到时在电脑上查：

```sh
adb logcat -d | grep "Accessing hidden"
```

告警行末尾的括号写着成员所在的名单和这次是放行（`allowed`）还是拦下（`denied`）。名单的写法各版本不同，
大致是：`greylist` / `unsupported` 不限 targetSdk；`greylist-max-o` / `max-target-o` 只放行 targetSdk 27 及以下；
`blacklist` / `blocked` 一律拦下。具体写法以实际日志为准。

## 检测项与原理

### 系统信息

安卓版本与 SDK、厂商 / 品牌 / 型号、系统版本号、本应用的风味与 targetSdk、是否可调试（调试包里放行的隐藏接口访问也会留告警）、
是否有隐藏接口限制（安卓 9 起）、放开隐藏接口限制的全局设置有没有被改过、应用内隐藏接口访问监听的自检结果、
安卓 12 起的运行时权限是否授予、蓝牙是否开启。

### 本机蓝牙地址

| 读法 | 原理 |
|---|---|
| `BluetoothAdapter.getAddress()` | 公开接口。安卓 6.0 起，没有系统级权限 `LOCAL_MAC_ADDRESS` 的应用拿到的是 `02:00:00:00:00:00` |
| `Settings.Secure` 的 `bluetooth_address` | 公开方法读一个系统设置项，系统蓝牙服务会把本机地址存在这里 |
| 系统属性 `persist.sys.bt_addr` | 反射调用 `SystemProperties.get`。有些车机把地址放在这个属性里，能不能读到取决于厂商和 SELinux |
| 系统属性 `ro.boot.btmacaddr`、`persist.service.bdroid.bdaddr`（补充） | 同上；这两个是常见的出厂地址、蓝牙栈地址属性 |
| 反射 `BluetoothAdapter.mService` 的 `getAddress()` | 公开的 `getAddress()` 走另一个系统服务，那里会给普通应用换成占位值；这里绕开它，直接调蓝牙服务本身 |

最后一项「结论」汇总哪些读法拿到了像样的地址、彼此是否一致。读到的地址还要和系统记录核对：
`adb shell dumpsys bluetooth_manager` 里的本机地址，或者另一台设备扫描到的车机地址。

### 监听 A、监听 B

用公开接口 `listenUsingInsecureRfcommWithServiceRecord` 开两个不加密、带服务记录的监听（服务名 `OpenHC-Probe-A` /
`OpenHC-Probe-B`），**两个同时开着**再读通道号，每种读法单独记一项：

| 读法 | 原理 |
|---|---|
| 1. `toString()` | 公开方法，输出里有「Channel: N」。N 来自服务端 socket 自己记的一个通道号字段 |
| 2. 反射 `mSocket` → `mPort` | 服务端 socket 里包着一个内部 socket（`mSocket` 字段）；开监听时协议栈把实际分配的通道号写回内部 socket 的 `mPort` 字段 |
| 3. 反射隐藏方法 `getChannel()` | 返回的是读法 1 的那个字段 |
| 4. `getPsm()`（安卓 10 起） | 公开方法，本意给 L2CAP 用，返回的也是读法 1 的那个字段 |
| 5. 反射内部 socket 的隐藏方法 `getPort()` | 返回 `mPort`，但在隐藏接口名单里是另一个成员，放行规则可能不同 |

每个监听最后有「结论」：所有拿到有效通道号的读法一致才算成功。监听 B 末尾再对比 A、B 的通道号，必须不同。

注意：对按 UUID 开的监听，原生安卓不会把实际通道号写回读法 1、3、4 用的字段，所以读到 -1 是正常的，
记为「失败」只是说这种读法没用，**不代表监听没开成**。

协议只要求把 **B** 的通道号告诉手机（A 由手机自己查 SDP）。A 用来交叉验证读法，并确认两个监听不同号。

### 备选：不建服务记录的监听

用隐藏方法 `listenUsingInsecureRfcommOn` 开一个不加密、不建服务记录、由协议栈分配通道的监听（老版本是带通道号参数的写法，
传 -2；新版本改成无参，两个都试，各记一项）。系统开这种监听时会把实际通道号写回服务端 socket 自己的字段，
于是公开的 `toString()` / `getPsm()` 就能读到。B 本来就是按通道号直连、不查 SDP，这种开法正好合用，
代价是开监听这一步要用隐藏方法。只试不加密的写法；带认证、加密的写法不符合协议，没有放进来。

### 接受连接（可选）

检测完后保持所有监听 60 秒，界面列出每个监听的 UUID 和通道号。有设备连入就记下对端地址并马上断开，
可以连多次；时间到或点「停止等待」后进入「结束」，关闭所有监听。

### 隐藏接口告警

汇总这次检测中系统报出的隐藏接口访问（成员签名），以及本进程 logcat 里与蓝牙、系统属性相关的 `Accessing hidden` 告警行。

## 预计结果

依据：AOSP 源码里的隐藏接口标注与名单（安卓 10、11、12、13、14 的源码分支，SDK 自带的 36.1 源码，安卓 9 只查了当时的放行名单），
以及构建时 lint 对 t36 风味的提示。**全部未经实测；厂商可能改动，一切以实测为准。**

| 项 | 安卓 6～8 | 安卓 10～12 | 安卓 13 及以上 |
|---|---|---|---|
| `getAddress()` | 占位值 | 占位值（12 起没授予运行时权限时抛 `SecurityException`） | 同左 |
| `bluetooth_address` 设置项 | 未核实 | 读到 null（安卓 10 源码：没有 `LOCAL_MAC_ADDRESS` 的应用读它，会被当作不存在） | 未核实；36.1 源码把它标成只对 targetSdk 31 及以下可读，t36 可能直接抛 `SecurityException` |
| 系统属性 | 取决于厂商和 SELinux | 同左 | 同左 |
| `mService.getAddress()` | 未核实 | `mService` 字段放行；蓝牙服务要求 `LOCAL_MAC_ADDRESS`，预计 `SecurityException`（安卓 10 源码） | 接口可能改了签名，未核实 |
| 读法 1、4（`toString()`、`getPsm()`） | -1（没有 `getPsm()`，记跳过） | -1 | -1（13、14、36.1 源码相同） |
| 读法 2（`mSocket` → `mPort`） | 能读（没有隐藏接口限制） | 两个字段都标为不限 targetSdk：**t36、t26 都放行** | 13、14、36.1 源码同样标注：**都放行**；lint 对 t36 也只给一般警告 |
| 读法 3（`getChannel()`） | 能调，但值是 -1 | 只放行 targetSdk 27 及以下：t26 放行、t36 拦下；放行也只读到 -1 | 名单未核实；lint 对 t36 报 “will throw an exception when targeting API 36 and above” |
| 读法 5（`getPort()`） | 能读 | t26 放行、t36 拦下 | 名单未核实；lint 对 t36 的提示同上 |
| 备选开法 1（带参数，传 -2） | 能开，`toString()` 读得到通道号（6.0 源码） | t26 放行、t36 拦下 | 13、14 名单未核实；lint 对 t36 的提示同上 |
| 备选开法 2（无参） | 没有这个写法 | 没有这个写法 | 36.1 源码里出现，名单未核实（lint 没有报） |

安卓 9：已核实读法 2 的两个字段和 `mService` 字段都在当时的放行名单里；其余各项未核实。

也就是说，按源码，**读法 2 在 targetSdk 36 下不该被拦**；targetSdk 26 比 36 多放行的是 `getChannel()`、`getPort()`
和带参数的备选开法。这正是要在真机上确认的：厂商有没有改，以及以后的系统版本会不会收紧。

## 核对通道号

「通道号与系统记录一致」才算真的可用。下面几种办法都要在**等待连接的 60 秒内**做（这时监听都开着），
任选其一，越往下越有说服力：

1. **dumpsys**：`adb shell dumpsys bluetooth_manager > bt.txt`，在里面搜 `OpenHC-Probe`、`fe35`、`fe36`、`RFCOMM`、
   `channel`、`scn` 等字样。各版本的输出格式不同，搜不到不代表探针读错了，换下面的办法核对。
2. **从另一台设备查 SDP**（只适用于 A、B，它们带服务记录）：在 Linux 电脑（BlueZ）上
   `sdptool browse <车机蓝牙地址>`，找到服务名 `OpenHC-Probe-A` / `OpenHC-Probe-B`，看它的 RFCOMM 通道号。
3. **按通道号直连**（这正是手机连 B 的方式）：在 Linux 电脑上

   ```sh
   python3 -c "import socket; s = socket.socket(socket.AF_BLUETOOTH, socket.SOCK_STREAM, socket.BTPROTO_RFCOMM); s.connect(('<车机蓝牙地址>', <通道号>)); print('已连上'); s.close()"
   ```

   探针界面出现「监听 B 有设备连入」，就说明这个通道号确实对，并且按通道号直连走得通。备选监听没有服务记录，只能用这个办法核对。
4. **按 UUID 连**：另一台安卓设备上用能按 UUID 连经典蓝牙串口（SPP）的调试应用，填 A 或 B 的 UUID。

第二台设备需要知道车机的蓝牙地址：可以用探针屏幕上读到的地址，或者让车机进入「可被发现」状态后在第二台设备上扫描。
不加密的监听一般不用配对；如果弹出配对请求，确认即可，不影响判读。车机上如果有别的应用也在监听同一个 UUID
（例如车机自带的手机互联服务），SDP 里会有多条记录，按服务名区分。

## 怎么下结论

先看 t36（与正式应用的 targetSdk 一致）：

| t36 的结果 | 结论 |
|---|---|
| 监听 B「结论」成功，A、B 不同号，且通道号核对一致 | 在这台设备上，正式应用保持 targetSdk 36 就能拿到 B 的通道号 |
| B 失败，但 t26 成功 | 只有低 targetSdk 才行：要么正式应用降 targetSdk（要另行评估代价），要么另想办法 |
| A、B 都失败，但「备选」在某个风味下成功且核对一致 | 第二个监听可以改用备选开法（依赖隐藏方法，只在那个 targetSdk 下可行） |
| 全部失败 | 这台设备上拿不到通道号，按通道号告诉手机这条路走不通 |

地址：「本机蓝牙地址」的结论成功、并且和系统记录一致，二维码就能自动带上真实地址；全部失败就要让车主手动填写或另想办法。

## 在哪些设备上测

每台设备上 t36、t26 都要测：

1. **安卓 10 车机**：主要目标。
2. **一台安卓 12 及以上的设备**，最好是安卓 14 或更新：蓝牙从安卓 13 起改为可单独更新的系统模块，隐藏接口名单可能不同。
3. 有条件再加一台安卓 9 以下的车机：没有隐藏接口限制，可以确认反射本身拿到的值对不对。

## 刻意不做的事

- 不用任何绕过隐藏接口限制的手法（元反射、豁免名单、改系统设置）：放行与否完全按系统对本应用 targetSdk 的规则，这正是要测的。
- 不配对、不发 BLE 广播、不改系统设置。所有监听在检测结束时关闭。
